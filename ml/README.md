# 빈자리 예측 (온디바이스 AI 준비)

수집기(`collector/`)가 5분마다 모은 서울 시영주차장 기록으로 **도착할 때의 빈자리**를 예측하는 모델을 학습하고, 단순 예측(기준선)과 비교한 리포트를 만들어요. 학습은 맥에서 하고, 고른 모델은 앱에 넣어 차 안에서 예측해요(1차 버전부터).

## 실행
```bash
~/miniconda3/bin/python -m venv .venv                 # Python 3.10 이상이면 돼요
.venv/bin/pip install -r ml/requirements.txt
.venv/bin/python ml/train_eval.py                     # → ml/reports/latest.md, latest.json
.venv/bin/python ml/train_eval.py --test-days 7       # 시험 기간을 직접 정할 때
.venv/bin/python ml/export_model.py                   # 기록 전체로 다시 학습 → 앱 모델과 Kotlin 대조용 정답 사례
.venv/bin/python ml/check_shipped.py                  # 앱 모델을 그 뒤 쌓인 기록으로 채점 → ml/reports/shipped.md, shipped.json
```
- 기록 3주 이상이면 마지막 7일, 그보다 적으면 마지막 1일을 시험 기간으로 써요.
- 학습한 모델은 `data/ml/models/models.pkl`에 저장돼요(저장소에는 안 올라가요).
- 주차장 종류(노상·노외)는 처음 한 번 서울시 API로 받아 `data/ml/lots_meta.json`에 저장해요. `.env`의 키가 필요해요.

## 학습 데이터 (`dataset.py`)
- **샘플:** (주차장, 지금 시각 t, 도착까지 남은 시간 h) 하나예요. h는 5·10·15·20·30·45·60분이에요.
- **정답:** t+h 시각의 실제 주차 대수예요. 앞뒤 2분 30초 안의 기록을 같은 시각으로 봐요.
- **입력:** 차 안에서도 구할 수 있는 값만 써요.

  | 입력 | 내용 |
  |---|---|
  | 주차장 | 주차장 번호, 총 주차면, 노상 여부 |
  | 시각 | 지금·도착 시각(분), 도착 요일, 주말, 공휴일 |
  | 지금 상태 | 점유율, 최근 15·30분 동안의 점유율 변화 |
  | 패턴 | 지금·도착 시각의 패턴 점유율, 두 값의 차이, 패턴에 쓴 날짜 수 |

- **패턴:** 앱 패턴표(`patterns`, 15분 칸)와 같은 규칙이에요.
  - 지난 28일 중 같은 요일 유형(평일/주말)·같은 칸(칸 시작 앞뒤 15분)의 날짜별 빈자리 중앙값을 다시 중앙값으로 묶고 반올림해요.
  - 그 값을 지금 총 주차면으로 나눠 점유율로 써요.
  - **기준 날짜보다 앞선 날짜만** 써서 미래 정보가 섞이지 않아요.
- **최근 변화:** 15·30분 전 기록의 빈자리를 지금 총 주차면으로 나눠요. 앱이 쌓는 실시간 기록에는 빈자리만 있어서 같은 방식으로 맞췄어요.
- **뺀 주차장:**
  - 하루 평균 2번 미만으로 값이 바뀐 곳은 값이 멈춘 것으로 보고 빼요. 기준은 `server/parking_core.py`의 `FROZEN_CHANGES_PER_DAY`이고, 앱도 같은 곳의 실시간 빈자리를 쓰지 않아요(`export_app_assets.py`).
  - 버스 전용 주차장도 빼요(앱 안내에서도 빼요).
  - 멈춤 판정은 전체 기록으로 해요. 같은 목록을 앱에도 넣을 거라서요.
- **빈 구간:** 맥이 잠든 동안처럼 도착 시각의 기록이 없는 샘플은 만들지 않아요.

## 비교 방법 (`train_eval.py`)
| 방법 | 내용 |
|---|---|
| 기준선 ① 지금 값 유지 | 도착할 때도 지금 빈자리가 그대로라고 봐요 |
| 기준선 ② 패턴표 | 위 패턴 규칙. 날짜가 3일 이상 있어야 써요(앱과 같아요) |
| 참고: 지금 앱 방식 | 패턴표 → 없으면 최근 30분 추세 → 없으면 지금 값 (근사) |
| 결정트리 앙상블 | `HistGradientBoostingRegressor`, 절대 오차로 학습, 주차장 번호는 범주로 써요 |
| 작은 신경망 | `MLPRegressor` (64, 32). 주차장 번호는 넣지 않아요 |
| 빈자리 확률 | `HistGradientBoostingClassifier`로 도착 시 빈자리가 1면 이상 있을 확률 |

- 두 회귀 모델은 '지금부터 도착까지 점유율 변화'를 예측하고, 빈자리(면)로 바꿔 화면처럼 반올림해요.
- **시험:** 시간 순서로 맨 뒤를 시험 기간으로 떼어요. 학습에는 도착 시각까지 시험 기간 전에 끝난 샘플만 써요.
- **지표:** 도착 10·20·30분 전과 5\~60분 전체의 평균 오차(면), 점유율 기준 오차(%p), 주차장 크기별 오차, 빈자리 있음/없음을 맞힌 비율이에요.

## 만차 판단 (대표 지표, 10/27)
운전자에게는 자리가 없어 돌아가는 쪽이 더 큰 손해라서, '도착 때 만차'를 참(True)으로 놓고 경고가 맞는지를 대표 지표로 봐요.
- **규칙:** 만차 위험 = max(지금 만차면 1, 1 − 빈자리 확률). 기준값보다 크면 '만차 위험'으로 경고해요. 지금 만차인 곳은 늘 경고해요.
- **대표 점수 F2:** recall(만차를 놓치지 않음)을 precision(경고가 맞음)보다 두 배 무겁게 봐요. F1으로 보면 헛경보를 거의 안 하는 '지금 만차만 보기'가 더 높게 나올 수 있어요.
- **기준값:** 학습 기간 마지막 하루(기록이 2주 이상이면 사흘)를 떼어 빈자리 확률 모델을 다시 학습하고, 그 기간에서 precision이 '지금 만차만 보기'보다 5%p 넘게 낮지 않은 값 중 F2가 가장 높은 값(0.05\~0.95, 0.01 간격)으로 정해요. 하한을 채우는 값이 없으면 precision이 가장 높은 값을 써요. `export_model.py`가 같은 방법으로 정해 `predictor.json`의 `full_risk.threshold`에 넣어요.
- **리포트 지표:** precision, recall(만차 포착), F1, F2, 전환 포착(지금은 자리 있다가 도착 전에 차는 경우), 헛경보, 자리 남 맞힘(지금 만차인데 자리가 나는 경우를 경고하지 않은 비율)이에요.
- 빈자리 확률 모델은 조기 멈춤을 꺼요. 켜 두면 기록이 조금만 늘어도 학습량이 달라져 결과가 크게 흔들렸어요.
- 기준값을 하루로 정하면 요일에 따라 흔들려요(10/27 기준 일요일로 정하면 0.89, 월요일로 정하면 0.60). 기록이 쌓이면 사흘로 정해요.
- precision 하한은 11/05에 넣었어요. F2는 낮은 기준값 쪽에서 거의 평평해서, 하한이 없으면 사흘로 정해도 0.12\~0.17까지 내려가 경고의 precision이 65\~70%로 떨어졌어요.
- 처음(11/05)에는 고정 하한 75%를 썼어요. 11/11 재학습의 검증 기간(11/08\~11)은 '지금 만차만 보기'도 precision 74.6%라 75%를 채우는 기준값이 없었고, 기준값이 0.92로 올라가 AI 경고가 '지금 만차만 보기'와 거의 같아졌어요. 그래서 그 기간의 '지금 만차만 보기'에 맞춘 상대 하한으로 바꿨어요.

## 앱에 넣기 (`export_model.py`)
- 기록 전체로 결정트리 앙상블 두 개(빈자리 변화, 빈자리 있을 확률)를 다시 학습해 `android/app/src/main/assets/predictor.json`으로 내보내요.
  - 노드 배열(JSON) 형식이고 1.1MB예요. APK 안에서는 압축돼 약 0.2MB예요.
  - 주차장 번호·노상 여부, 공휴일, 입력 순서도 함께 들어가요.
- 앱의 `core/SpacePredictor.kt`가 이 파일을 읽어 차 안에서 예측해요.
  - 입력은 앱이 가진 값(실시간 값, 1분마다 쌓는 최근 기록, 앱 DB 패턴표)으로 만들어요.
  - 결정트리는 scikit-learn과 같은 규칙으로 따라 내려가요. 범주 분기와 값이 없을 때의 방향도 같아요.
- **대조 테스트:** `export_model.py`가 실제 기록에서 고른 290개 상황의 입력·예측값·확률을 `android/app/src/test/resources/predictor_golden.json`에 써요.
  - Kotlin `SpacePredictorTest`가 같은 상황에서 입력 16개, 빈자리, 확률이 모두 같은지(차이 1e-12 미만) 확인해요.
  - 290개에는 최근 기록 없음, 패턴 있음·없음, 주말·공휴일, 도착 시간 범위 밖, 모델이 모르는 주차장이 섞여 있어요.
- **화면 스위치:** `android/app/build.gradle.kts`의 `AI_PREDICTION_ON_SCREEN`이에요.
  - 1차 버전부터 `true`예요(10/25 결정). 도착 전 비교 카드에 'AI 예측 · 도착 때 약 N면 · 빈자리 확률 N%'로 보이고, 빈자리 확률 50% 미만인 곳은 추천 순서에서 뒤로 가요.
  - 끄면 화면은 예전 방식(패턴표 → 추세 → 지금 값)을 쓰고, 모델 예측은 로그에만 남아요.
  - 어느 쪽이든 예측은 로그(`StatioAI`)에도 남아요. 예: `ai lot=171721 eta=34.0 now=730 base=730(CURRENT) ai=742 p=1.000`
- 모델을 다시 만들면 `export_model.py` → Kotlin 테스트 → APK 빌드 순서로 해요. 패턴 입력의 품질은 앱 DB 패턴표에 달려 있어서, 패턴표도 `datapipe/export_app_assets.py`로 먼저 새로 만들어야 해요(지금 앱 모델은 10/27 01:43까지의 5일치이고, 앱 DB 패턴표는 칸마다 최대 2일치예요).

## 앱 모델 사후 채점 (`check_shipped.py`, 11/12)
`train_eval.py`는 기록을 나눠 새로 학습하지만, 이 스크립트는 **앱에 넣은 모델 파일을 다시 학습하지 않고 그대로** 읽어 모델을 만든 뒤에 쌓인 기록으로 채점해요. 실제 쓰임에 가장 가까운 숫자예요.
- 모델 파일의 학습 기록 끝 시각(`data.to`) 뒤의 샘플만 써요. 주차장 번호·노상 여부는 모델 파일의 것을 써요.
- 먼저 파이썬 채점기가 Kotlin 대조용 정답 사례와 같은 값을 내는지(차이 1e-9 미만) 확인하고, 다르면 멈춰요.
- **앱 안 조건:** 패턴 입력은 앱 DB 패턴표 한 칸에서 가져와요(`export_model.device_features`와 같은 규칙). 패턴 입력을 학습 규칙(`dataset.py`)으로 만든 결과도 참고로 적어요.
- 기준선·지표는 `train_eval.py`와 같고, 날짜별 결과와 패턴표 오차가 큰 주차장도 적어요.
- 11/12 결과(11/11 모델, 11/11 22:59 \~ 11/12 20:40, 샘플 13.4만 개, 도착 때 만차 3,164개): 만차 판단 precision 75.5%·recall 84.0%·F2 0.822(지금 만차만 보기 0.784), 빈자리 오차 2.40면(지금 값 유지 4.79면, 패턴표 6.56면).
- 10/29 결과(10/27 모델, 샘플 28.7만 개, 도착 때 만차 8,326개): precision 77.9%·recall 84.8%·F2 0.833(지금 만차만 보기 0.792), 빈자리 오차 2.44면(지금 값 유지 4.79면, 패턴표 7.77면). 자세한 건 [reports/shipped.md](reports/shipped.md)에 있어요.
- 모델을 다시 만든 뒤에는 며칠 기다렸다 다시 돌려요. 모델을 만든 뒤 쌓인 기록이 없으면 그렇다고 알려 주고 멈춰요.
